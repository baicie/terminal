## 1. 迁移快照保留策略（#62）

### 改前行为（证据）

`backup_database_before_migration` → `unique_destination` → `snapshot_before_migration`：只有「找一个
没被占用的名字」和「写 + 读回校验」，**没有任何删除路径**。迁移持续失败的机器每次启动新增一份整库副本，
目录只增不减。

### 失败证明（先写测试后实现）

先只加测试与被调用但空实现的函数骨架（`prune_old_snapshots` 返回 0），再跑：

    ---- pruning_keeps_the_newest_snapshots_and_removes_the_oldest stdout ----
    assertion `left == right` failed: eight snapshots under a cap of five must remove exactly three
      left: 0
     right: 3
    ---- pruning_never_deletes_anything_that_is_not_a_snapshot_of_ours stdout ----
    assertion `left == right` failed: only the eight real snapshots above the cap go
      left: 0
     right: 8

    test result: FAILED. 5 passed; 2 failed

### 改后行为

- `MAX_SNAPSHOT_COPIES = 5`：恢复时真正有用的是「刚被迁移弄坏之前」那一份，其后四份覆盖第二、三次
  失败尝试、一次重启和一份用于对照的旧版本；更早的与「数据库文件本身 + 用户自己的导出」重叠，
  而每一份都是一个完整数据库，所以这个上限就是该目录的磁盘上界 `N × 数据库大小`。
- 守卫（三条都写死在实现里）：**不递归**（只 `read_dir` 一层）、**只认普通文件**（`file_type().is_file()`，
  目录/符号链接即使名字像也不动）、**只认名字严格匹配** `pre-migration-<纯数字>.db` 或
  `pre-migration-<纯数字>-<n>.db`。
- 排序按文件名里的 epoch-ms 戳（不依赖 mtime，因此测试与文件系统时间精度无关），删最旧的若干份。
- 删除失败：`tracing::warn` 后继续，函数签名不返回 `Result`，因此结构上不可能阻断迁移。
- 调用点在**新快照校验成功之后**：先删后写会在证明有替代品之前丢掉好的旧副本。

### 测试与实际输出

    test db_import::backup::tests::pruning_keeps_the_newest_snapshots_and_removes_the_oldest ... ok
    test db_import::backup::tests::pruning_never_deletes_anything_that_is_not_a_snapshot_of_ours ... ok
    test db_import::backup::tests::a_snapshot_that_cannot_be_deleted_does_not_fail_the_prune ... ok
    test result: ok. 7 passed; 0 failed; 0 ignored

第三条用只读目录制造真实的 `remove_file` 失败（`#[cfg(unix)]`）：3 份快照、cap=1，删除全部失败，
返回 0 且不 panic、不报错。

## 2. `catch` 审计：仍在吞掉真实错误的地方

### 方法

自动枚举 `packages/frontend/src`（排除 `*.test.*`）里的 `} catch {`（**60 处**，无绑定裸 catch）
与 `catch (`（169 处，含绑定形式），逐个读「catch 体内的第一句」判断它把失败变成了什么；`src-tauri`
侧对应形态是 `let _ = ` / `.ok()`（**84 处**），其中绝大多数是 UI best-effort（`window.show()`、
`emit`、测试清理）与诊断通道。

### 判定标准

只问一件事：**这个 catch 是否用「捕获全部失败」去实现「只处理其中一种已知失败」**——即 Phase 8.9
duplicate-column 的同类。是则修；不是（调用方语义本来就是「拿不到就用兜底」）则记录不改。

### 已修（1 处，同类型的最严重一例）

| 位置 | 吞掉什么 | 应该只吞什么 | 结论 |
| --- | --- | --- | --- |
| `service/vault.ts` `getHostCredential` / `deleteHostCredential`（原 4 个空 catch，注释写「Key not found, ignore」） | `vault_get`/`vault_delete` 的**全部**失败：`vault_locked`、`corrupt`、`decrypt_failed`、`uninitialized` 以及 IPC 失败 | 只有 `key_not_found` 是「这半边凭据不存在」 | **已修** |
| `service/vault.ts` `KNOWN_VAULT_ERROR_KINDS` | 后端 `VaultErrorDto` 会发 `key_not_found`，前端集合里没有它 → 一律归 `unknown`，所以上面那个「只吞 not found」当时**写不出来** | 收全后端实际会发的 kind | **已修**（新增 `key_not_found`） |

失败证明（改前）：

    × keeps the backend kind for a key the vault does not hold
      AssertionError: expected 'unknown' to be 'key_not_found'
    × does not report a locked vault as "no stored credential"
      AssertionError: promise resolved "{}" instead of rejecting
    × does not report a failed delete as deleted
      AssertionError: promise resolved "undefined" instead of rejecting

## 3. 单轮页数上限的显式状态

`MAX_SYNC_PAGES = 25` 的本意只是「挡住 `hasMore` 永远为真的坏响应」，但循环耗尽后直接 `return`，
调用方无法区分「窗口读完了」与「这一轮读不动了」，于是照常推送、照常写 `lastSyncAt`。

失败证明（改前）：

    × reports the page limit instead of claiming the round finished
      AssertionError: expected "vi.fn()" to be called undefined times, but got 25 times
    （该断言是 `toHaveBeenCalledTimes(MAX_SYNC_PAGES)`，常数当时未导出故显示 undefined；
      同一条用例随后还断言 `pushChanges` 未被调用、`lastSyncAt` 仍为 null，两条当时都不成立）

改后：`PullOutcome.hasMore` 暴露该状态；`sync()` 在该轮**不推送**（从半张图推送等于用未对账的版本
提交写入）、**不写 `lastSyncAt`**（它只表示「最后同步时间」，不能替没读完的拉取背书）、不丢本轮
已发现的冲突，并以日志说明将从断点续拉。游标本来就逐页持久化，所以停止不产生重投。

## 4. resync 时本地旧数据的安全清理

**先论证哪种更安全。** 三个候选：

1. 不删（现状）：服务端已删除的行永远可读，且下一次推送会把它推回服务端——**复活已删除数据**，
   多人协作下等于把别人的删除撤销掉。
2. 收到 `resync` 就清空本地团队数据：最"一致"，但会删掉**尚未推送的本地编辑**（`version IS NULL`
   或 `dirty = 1` 的行），那是拿一个还在用户手里的改动换一致性。
3. 只删「快照能证明不存在」的行：**采用**。

判定条件（同一轮必须全部满足，缺一条一个字节都不删）：`resync === true`（服务端自称全量）、
`hasMore === false`（整窗读完）、`authorizedTeams !== null`（有作用域）、行 `version IS NOT NULL`
（服务端见过这一行）且 `COALESCE(dirty,0)=0`（没有未送出的本地编辑）。

代价写在明处：一条「服务端已删、本地又改过」的行会保留，由下次推送以 UPDATE 提出，服务端以**可见
冲突**拒答——宁可让用户看见一次冲突，也不静默删他的编辑。

失败证明（改前）：`AssertionError: expected "vi.fn()" to be called with arguments: [ [ 'team-1' ], [ 'still-there' ] ]`
（即：客户端从未调用任何清理）。反例用例（增量轮 / 截断轮 / 无作用域）在改前是"空过"，
改后仍必须保持不调用，用来防止把删除条件放宽。

## 5. 三条满载 flaky（#61）：诊断结论，不改阈值

### 测到的数

| 场景 | terminal-bootstrap | workspace-switcher | keychain |
| --- | --- | --- | --- |
| 单独跑 3 个文件（8 核，maxWorkers=4） | 177 ms | 138 ms | 188 ms |
| 同上 + 10 个 CPU 占满进程（8 核） | 276 ms | 307 ms | 374 ms |
| 全量 150 文件门禁（真正的门禁形态） | 144 ms | 186 ms | 232 ms |
| 全量门禁复跑（第 2 次） | 145 ms | 229 ms | 258 ms |

### 结论

1. **不是「真实异步工作在 CPU 争抢下变慢」**：真实争抢（10 个占满核的进程）只让它慢 1.5–2 倍，
   离注释里的 1000 ms 断言期限仍有 3 倍余量；全量门禁下这三个用例甚至与单独跑**同量级**。
2. **也没有掩盖别的问题**：三个用例内没有任何生产定时器在等（唯一真实定时器是 terminal-bootstrap
   刻意设的 `appLoadTimeoutMs: 50`，用来制造「chunk 永不落地」）；等待对象都是已 resolve 的 mock
   Promise 与 React 状态提交，放宽期限不可能让任何断言变得更强或更弱。
3. issue 里记录的 1922 / 5169 / 6077 ms 中，后两个**已超过 vitest 默认 5 s 测试超时**，说明那两次
   不是"用例变慢"，而是 **worker 被停顿了**（本机 `environment 162 s`、`import 36 s` 的累计量说明
   jsdom 环境与模块图才是重活）。那种停顿与用例写法无关，调 `testTimeout` 只会让它更晚才被发现。

因此本轮**不调任何 timeout、不改任何断言、不跳过用例**。判定为：需要 CI runner 的核数与堆数据
（或带时间戳的 worker 停顿日志）才能决定是否要动门禁参数；在此之前动它就是拿掉门禁。
可复现步骤：在 2 核环境跑 `npx vitest run --maxWorkers=4`，同时采样 `vm_stat`/`process.memoryUsage`。

## 6. `@ts-nocheck`（#64）

任务书给的两条路都实测不可行：

- **给 team-server tsconfig 加 `@/*` → `../frontend/src`**：`baseUrl` 已被 TS 弃用（`error TS5101`），
  去掉它只写 `paths` 后，前端整棵树被拉进 server 程序，立刻报
  `TS6059: File '…/frontend/src/…' is not under 'rootDir' …` 以及一批 `TS2554`（前端代码在本
  tsconfig 下根本编译不过：没有 DOM lib、模块解析不同）。
- **在 spec 里改相对路径导入**：同一个 `TS6059`，还会把同一棵前端树拉进程序。

实际采用代价更小且更诚实的一条：**逐个 import 抑制**。移除 `@ts-nocheck` 后 `tsc` 立刻报 7 条：

    6 × TS2307: Cannot find module '@/store/…' or its corresponding type declarations
    1 × TS2352: Conversion of type 'Record<string, SQLOutputValue>' to type 'LocalRow' may be a mistake

前 6 条按行加 `// @ts-expect-error`（各自带同一句说明），第 7 条是 `@ts-nocheck` 藏起来的**真实类型
错误**，改成 `as unknown as LocalRow` 让形状在使用点继续被检查。此后再 `tsc --noEmit` 通过，
`eslint src` 0 error。文件顶部保留 `/* eslint-disable ts/ban-ts-comment */`（抑制注释仍然受规则约束，
需要显式豁免，这本身也是记录）。

比 `@ts-nocheck` 严格在哪：整个文件（断言、harness、SyncService 调用）重新参与类型检查；6 处抑制
是**逐行且自校验的**——哪天别名能解析了，`@ts-expect-error` 会因为"没有错误可抑制"而变红。

## 8. 门禁四分类

| 类别 | 门禁 | 依据 |
| --- | --- | --- |
| **blocking** | `Frontend quality`（typecheck / lint / vitest）、`Team Server quality`（typecheck / lint / vitest / prisma migrate + schema 校验 / 真实 PostgreSQL 并发套件）、`Production source-size gate`、`Rust quality`（`cargo fmt --check` / `clippy -D warnings` / `cargo test`）、`Team Server container`（compose 校验 + 镜像构建）、`Tauri build` 矩阵（含 macOS/Windows/Linux 安装链 + 数据保留验证、PowerShell 解析器校验）、本地 `scripts/verify.mjs` | 失败必须红；本轮全部实跑通过（§9） |
| **diagnostic** | `zsh probe diagnostic`（`ci.yml` 中 `continue-on-error: true`，只上传 transcript，不判定）；启动插桩通道 `startup_stage` / `startup_stage_failed`（`traceStage`/`traceStageFailed` 只采集，`catch` 不抛） | 只采集证据，不阻塞 |

   幽灵行会留到下一轮 resync 再清。方向是"晚清一次"而非"误删"。
5. **单条 `dirty` 行会与服务端的删除冲突**：这是有意选择的代价（§4），冲突会出现在 `syncConflicts`。
