# e2e-02 在 Linux 上的列数滞后：两次修法都失败，未修

**判定：UNFIXED（既有 flake，与 DDQ 改动无关）。** 本文件记录两次失败的尝试与已确证的事实，
供下次接手的人不必重走。

---

## 症状

Linux runner 上 `e2e-02-layout` 间歇失败，报「width(s) broke the 60-column floor」。
两次观测（run `46124241301`、`46145389470`）的读数形状完全相同：

| 请求宽度 | `predictedCols` | 状态栏 `cols` |
| --- | --- | --- |
| 1440 | 82 | **142** |
| 1280 | 82 | **142** |
| 1024 | 60 | **60** |
| 900 | 60 | **60** |

两对相同值，而 `predictedCols` 随宽度变了。**状态栏的 `cols` 是上一次 resize 的残留值**。

同一 shape 在 macOS 上没出现过。重跑 Linux job 会通过——所以是时序，不是逻辑错误。

---

## 根因（已确证）

`readCols()` 从状态栏文本读 `cols×rows`，而状态栏的数字来自 xterm 的 `onResize` 回调，
它在布局决策之后才触发。`readCols` 一读到能解析的数字就返回，所以**resize 之后的第一
个可读数字可能是上一个宽度的**。

---

## 尝试一：两次读数一致才返回 —— 失败

**为什么不成立**：陈旧值会重复。1024 与 900 都读到 60，连续两次相同，轮询接受它。

已在本地复现失败（`last text: "ConnectedLocal112×49"` 之前的那次运行）。

## 尝试二：与画布几何交叉核对 —— 失败

判据是 `|cols - canvasWidth/cellWidth| <= 1`。

**实测结果**：`reading: {cols: 112}` 而 `expected: 114`，**差 2 列**。
`canvasWidth / cellWidth` 与 xterm 实际列数之间有固定偏差（内边距或滚动条占宽），
幅度超过我给的 1 列容差。

**这条更重要**：它说明「用几何推列数」这条路本身不精确，不能作为判据。要修得先
测出那个固定偏差是多少、是否随宽度变化——那是另一轮的工作。

两次失败后已回退到 `origin/main` 的版本，**没有留下半成品**。

---

## 现在是什么状态

- `e2e-02` 的代码与 `main` 一致。
- Linux GUI E2E 是 **informational job**（`continue-on-error: true`），不是阻塞门禁。
- 它会在 Linux 上间歇变红并让 `required` 失败——这就是需要修的动机。

## 下次可以试的方向（都没有验证过）

1. **让 `readCols` 等到真正的 resize 事件**：xterm 的 `onResize` 是产品自己订阅的，
   探针可以记录"最近一次 resize 发生在何时"，`readCols` 等到那个时间戳晚于本次
   resize 请求。这需要一个探针字段，是本轮没有的。
2. **先测出 `canvasWidth/cellWidth` 与列数的固定偏差**，再把它作为已知量代进去。
   上面实测是 2 列，但只测了一个宽度，不知道是否恒定。
3. **不读状态栏，直接用探针的 `snapshot().cols`**（它读 `terminal.cols`）。
   e2e-02 在移动断点以下已经在用它——问题是断点以上为什么没用。
   这条最可能对，也最没被验证过。

## 为什么这一轮停下

任务书的纪律是「外部条件阻塞时记录真实原因，继续其它独立任务」，而这里不是外部条件，
是**我两次都没修对**。继续试第三次的成本，比把它如实记录、让下一个接手的人从这三个
方向里挑一个要高。

**没有把断言放宽**，也没有加 `continue-on-error` 让它变绿——那会让一个真实的时序缺陷
永久消失。
